Plausible is not checked

Ryan Tornberg, September 2026

A small feature shipped in two rounds. The first round added a rule to a sign-up flow and went through review. The second round went back to finish a gap the first round had knowingly left open. It found four defects in the first round's work, and two more in the environment that had verified it.

None of the individual fixes had been careless. Most of them were right. What failed was the process that decided when something counted as done, and it failed the same way again and again.

A claim was recorded at the point where it became plausible, not at the point where it became checked.

What that looks like

Three examples, each of them reasonable at the time:

  • "The rule is enforced" was written down when the screen stopped letting a user continue. The server behind the screen still accepted the request when it was sent directly.
  • "That case is partly covered" was written down when a method with the right name turned up in a search. Nobody had read what the method did.
  • "Verified in the browser, both tiers" was written down when one tier passed. The other tier could not load its settings at all.

Each claim was a sensible guess. None of them had been checked, and each one took a second round of work to correct.

Why AI makes this worse

This failure is older than AI. An AI agent makes it faster. An agent writes fluent, confident status updates, and it produces plausible claims far faster than anyone can check them. If "done" means "a reasonable person would believe it," an agent will reach done constantly, and the defects come back later.

Surveys this year say most developers use AI tools and fewer than a third trust what the tools produce. I don't think the answer is to trust the tools more or less. The answer is to change what "done" means, so that trust stops depending on anyone's judgment in the moment.

What changed

Two of the cheapest steps had been skipped at the start: I didn't review my own diff, and I didn't run the change in a real environment before calling it ready. When both steps finally ran, they found problems at once. The first review found three defects in one pass. The first real run found that the new screen could be bypassed with the keyboard.

So the rules changed, and each rule went into the checklist that should have caught the problem, not into a memo:

  • Every claim is marked verified or inferred. "Verified" means someone ran the check and can point to the output. Everything else is labeled a guess, which is fine, as long as it's labeled.
  • Review happens in a fresh context. The session that wrote the change doesn't approve it. A separate pass reads it cold, the way a stranger would.
  • A fix after review gets its own review. The first time we skipped this, a second look at the fix found four more defects. The review-and-fix loop now has a limit: two automated rounds, then a person takes over.
  • A lesson isn't recorded until the checklist that should have prevented it is changed, in the same commit. A lessons log that changes nothing is a diary.

What it costs

Checking isn't free. In one measured stretch of agent-assisted work, about one action in eight was a check: a test run, a build, a browser session, or a documentation gate. The other seven were changes. That ratio is the price of speed you can trust, and it's cheap next to a second round of fixes that nobody planned for.

The habit is simple to state and hard to keep: don't write it down as true until you have seen it be true.
