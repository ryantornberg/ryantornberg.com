How an agent workspace works

Ryan Tornberg, September 2026

A capable model plus a large old codebase does not produce reliable work. It produces confident work, which is different. The gap between the two is filled by a small amount of infrastructure that most teams have not built yet.

This is the pattern I build and run. It is deliberately boring: text files, generated indexes, and checks that fail loudly. Nothing here is specific to one employer, and any team can copy it in a week.

1. The third thing

An agent starting work on your codebase draws on two sources. The model brings general competence. The repository says what the software currently is. Neither holds the third thing: what only your organization knows.

That third layer is small. It is the facts a model cannot derive and a reader cannot infer: which of two similar directories is the live one, which branch was abandoned and why, what the team calls a thing versus what the code calls it. Written down once, it stops being tribal knowledge and starts being context any session can load.

2. The loop, and what each part prevents

Context alone decays. The moment it goes stale it becomes worse than nothing, because it lies confidently. So each piece of the workspace is paired with something that fails when it stops being true.

The eval loop is the part teams skip. When an agent goes wrong because the guidance told it to, the fix is not just correcting the guidance. It is adding a case that reproduces the mistake, so the next edit cannot reintroduce it. Guidance is code; treat it that way.

3. Speed you can defend

"We ship faster with AI" is unfalsifiable and everybody says it. Two ratios make it checkable, and both come from the session logs rather than from anyone's impression.

A check is a test run, a build, a browser session, or a documentation gate: an action whose only purpose is to find out whether the work is real. If that share collapses, the team is producing plausible output again, and the number says so before the defects do.

4. Adoption, measured honestly

The failure mode of internal tooling is a mandate: everyone is told to use it, usage is reported as success, and nobody asks whether it helped. The alternative is to measure the thing the workspace exists to remove.

What it costs to copy

About a week of one engineer's time for the first version: an instruction file, a symbol index, three or four checks wired into continuous integration, and the habit of turning each escalated question into a fix. The expensive part is not the tooling. It is deciding that unverified output is unfinished work, and then holding to it when a deadline argues otherwise.
